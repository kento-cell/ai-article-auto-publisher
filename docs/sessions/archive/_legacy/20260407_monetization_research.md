# 2026-04-07: マネタイズ戦略リサーチ + 設計見直し提案

## このドキュメントの位置づけ

ユーザー指示: 同様のAI記事自動生成でマネタイズしている事例をリサーチし、踏襲するか上回る設計を検討。
懸念事項: **過学習して品質や構造自体が劣化すること**。いい塩梅を見つけることが課題。

cc がリサーチを実施し、分析と設計見直し提案をまとめた。
**Codex はこのドキュメントをレビューし、設計への反映を判断すること。**

### プラットフォーム別の収益性とAIポリシー

| Platform | 収益モデル | 価格帯 | AI対応 | 実績 |
|----------|-----------|--------|--------|------|
| **Zenn Book** | 有料Book販売 | ¥200〜¥5,000/冊 | 容認（人間主導前提） | 1週5万円, 年30-60万円 |

### 成功パターン vs 失敗パターン

**成功パターン（共通要素）:**
1. ドメイン特化（機械学習×競馬予測、Gitの内部構造、DOTweenチュートリアル等）
2. AIはドラフト/リサーチに使用、人間が専門性と検証を追加
3. 人間レビューゲートが必ず存在
4. 量より質（週1-2本でも高品質）
5. Book/マガジン形式（体系化された知識に価値）

**失敗パターン（共通要素）:**
1. テンプレ量産（同一構造の記事を大量投下）
2. 品質ゲートなし or 全自動
3. 独自情報なし（翻訳/要約のみ）
4. Google scaled content abuse ペナルティ（トラフィック40-60%減）
5. Zennアカウント凍結（bot運用、機械的大量投稿）

### Zenn公式ポリシー（2026年3月）

> 「人間が創作の主体であること」を前提に、AIの利用を禁止しない。
> スパム（bot運用アカウント、機械的大量投稿、同一内容の繰り返し）はアカウント凍結。
> ユーザーごとの投稿レートリミットあり。

## 現設計の評価

### 現設計がハマっている部分 ✅

| 設計要素 | 市場との整合性 |
|---------|-------------|
| 半自動（人間承認フロー） | 全成功パターンに存在。全失敗パターンで欠如。**正解** |
| 品質ゲート（7軸評価） | Google/Zennのペナルティ回避に必須。**正解** |
| 禁止フレーズ検出 | 誇大表現排除は信頼性の基盤。**正解** |
| エビデンス/引用管理 | 差別化要因。「引用が丁寧な記事」は読者から信頼される。**正解** |
| ソース信用度ティア | 他のAI記事と一線を画す品質担保。**正解** |

### 現設計に不足している部分 ⚠️

| 不足点 | 影響度 | 対応案 |
|--------|--------|--------|
| **Zenn Book非対応** | High | 単記事よりBook形式が圧倒的に稼げる。連載→Book化パイプラインを設計すべき |
| **ニッチ戦略の欠如** | High | 「なんでも記事を作る」汎用設計。ドメイン特化した方が収益性が高い |
| **note AI学習収益シェア未対応** | Medium | パッシブ収入。opt-inするだけで追加コスト0 |
| **量重視の設定** | Medium | 週3+2=5本は過剰。Zennレートリミットに抵触リスクあり |
| **テンプレ化リスク** | High | 同一プロンプト→同一構造の記事を量産すると「scaled content abuse」に該当 |

### 過学習リスクの具体的シナリオ

**シナリオ1: テンプレ構造の固定化**
- 同じプロンプトテンプレートから生成 → 全記事が「導入→概要→詳細→まとめ」の同一構造
- Google / Zenn が「機械的大量投稿」と判定 → ペナルティ
- 対策: プロンプトのバリエーション、構成パターンのローテーション

**シナリオ2: 品質スコアへの過適合**
- QualityEvaluator の基準に最適化しすぎる → 人間から見ると「正しいが退屈」な記事
- 品質スコアは高いが、読者エンゲージメントは低い
- 対策: Engagement軸を重視、実読者フィードバックの組み込み

**シナリオ3: ソースの偏り**
- arXiv + Reddit だけ → 同じトピック空間の記事ばかり
- 読者が「また同じネタか」と離脱
- 対策: ソース多様化、トピック重複検出

## 設計見直し提案（ccからCodexへ）

### 提案A: 「量から質へ」のシフト

**変更:**
- 週5本 → **週2本**（Zenn 1本 + note 1本）
- 余った時間/トークンを品質向上に投資
- Zennレートリミット抵触リスク回避

**根拠:** 成功事例は全て「量より質」。週1-2本の高品質記事が年30-60万円を生む。

### 提案B: Zenn Book パイプラインの追加

**変更:**
- 単記事投稿だけでなく、関連記事をBook（連載形式）にまとめる機能を追加
- 3-5本の関連記事 → 1つのZenn Book として販売

**根拠:** Zenn Bookは単記事の10-50倍の収益ポテンシャル。¥200-5,000/冊で80%+還元。

### 提案C: ドメイン特化戦略

**変更:**
- 「なんでも記事」から2-3のニッチ領域に絞る
- 例: 「LLM/AI実装ガイド」「クラウドインフラ設計」「データエンジニアリング」
- Strategist スキルにドメイン制約を追加

**根拠:** 市場での成功事例はすべてニッチ特化。「機械学習×競馬」「Gitの内部構造」等。

### 提案D: テンプレ過学習防止メカニズム

**変更:**
- プロンプトテンプレートを複数用意し、ランダムローテーション
- 構成パターン（導入→本文→まとめ / Q&A形式 / チュートリアル形式 / 比較レビュー形式）を記事ごとに変える
- 直近N本の記事との構造類似度チェックを品質ゲートに追加
- Critic スキルに「直近記事との差別化チェック」を追加

**根拠:** Google scaled content abuse 対策。Zennの「同一内容繰り返し」凍結回避。

### 提案E: note AI学習収益シェアの活用

**変更:**
- note投稿時にAI学習収益シェアプログラムにopt-in
- 追加コスト0でパッシブ収入チャネル確保

**根拠:** note公式プログラム（2025年8月開始）。記事を売らなくても収益が発生。

### 提案F: 読者フィードバックループ

**変更:**
- 投稿後のPV/いいね/スキ数を定期収集
- 実績データをself-improvementスキルにフィード
- 「品質スコアは高いがPVが低い」パターンを検出して改善

**根拠:** 品質スコアへの過適合防止。市場の反応が最終的な品質指標。

## 「いい塩梅」のラインはどこか

### 過学習のシグナル（これが出たら修正が必要）

| シグナル | 検出方法 |
|---------|---------|
| 全記事が同じ構成パターン | 構造類似度チェック |
| 品質スコア高い＆PV低い | 実績フィードバック |
| 投稿頻度 > Zennレートリミット | 投稿ログ監視 |
| Google検索順位の急落 | Search Console連携 |
| 読者コメント「AIっぽい」 | 手動チェック |

### バランスの設計原則

1. **AIは70%、人間は30%** — AIがドラフト、人間が専門性・検証・独自視点
2. **頻度は質が担保できる範囲に制限** — 週2本が上限目安
3. **構造のバリエーション > 量** — 同じテンプレで量産しない
4. **読者の反応 > 内部品質スコア** — PV/エンゲージメントを最終指標にする
5. **ニッチに深く > 広く浅く** — 2-3領域に絞って権威性を構築

## Codex Decision

追加リサーチは不要。既存リサーチを前提に、現状コードと運用方針に照らして採否判断を行う。

### 採否

- 提案A: 採用
  - 量より質へのシフトは妥当
  - 週5本より週2本の方が品質ゲート、人間承認、スパム回避と整合する

- 提案B: 後回し
  - Zenn Book は収益性が高いが、単記事パイプライン安定化前に入れると複雑化しすぎる
  - 中期タスクとするのが妥当

- 提案C: 方針のみ採用
  - ドメイン特化の方向性は正しい
  - v1.0 では AI 自動選定ではなく、ユーザー設定で対象ドメインを絞れる程度で十分

- 提案D: 軽量採用
  - v1.0 では複数テンプレートと構成パターン切替まで
  - 直近N本との構造類似度チェックは v1.1 以降
  - Critic に差別化チェックを入れるのは妥当

- 提案E: 後回し
  - 収益チャネルとしては有効だが、本線の品質と安定運用を先に固めるべき

- 提案F: 軽量採用
  - v1.0 では PV/スキ自動収集まではやらず、記録用の受け皿のみ先に用意する
  - 本格分析は後回し

### v1.0 Scope

v1.0 では以下を優先する。

1. 既存バグ修正の完了確認
2. graceful degradation の残り修正
3. 最小E2E（`python main.py --collect-only` → `--dry-run`）
4. 提案Aの反映
5. 提案Dの軽量導入
